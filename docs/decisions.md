# NetWatch 2.0 decisions log

Decisions taken while completing 2.0 where the brief was ambiguous or where the code already went another way.
Each entry: what was decided, and why.

| # | Date | Topic | Decision | Why |
|---|---|---|---|---|
| 1 | 2026-11-21 | Starting point | 2.0 work starts from 1.4.0 (Phases 4 and 5 were committed after the 68 % status report), not from 1.2.0. Each work package fills the gaps between 1.4.0 and the 2.0 brief instead of re-implementing what exists. | Avoids duplicate code and keeps 1.3/1.4 data compatible. |
| 2 | 2026-11-21 | Configuration precedence | defaults → data-folder `appsettings.json` → `NETWATCH_*` environment variables (`NETWATCH_Https__Port`) → command line (`--Https:Port=8444`). | The settings file used to be added last, so it silently overrode the command line. |
| 3 | 2026-11-21 | Start-up test | `--self-test` starts the full host (databases, seeding, hosted services, Kestrel), runs `SelfTest:Seconds` (default 5), stops, exits 0. The unit test runs it on an empty temp folder with `--simulate --Https:Port=0`, and two tests call `HasPendingModelChanges()` on both EF contexts. | Catches a missing migration (the 1.2.0 working-tree crash) and any start-up exception in CI. The same switch can be used after installation. |
| 4 | 2026-11-21 | Version | `2.0.0-dev` during development. Inno Setup's `VersionInfoVersion` must be numeric, so `build.ps1` passes `/DNumericVersion` (the version without its pre-release suffix). | Inno Setup rejects `2.0.0-dev` there. |
| 5 | 2026-11-21 | WEF per DC | `UseForwardedEvents` = every DC uses Windows Event Forwarding; otherwise `ForwardedDcs` (name, short name or IP) lists the DCs that use it and the rest are read remotely. Stored in the `dc` settings, so no schema change. | Brief asks for a per-DC choice; a settings list avoids a migration and works for DCs added later by name. |
| 6 | 2026-11-21 | 4624 noise | `SuccessfulLogonIgnoreSources` (IP, IPv4/IPv6 CIDR, or workstation name) drops successful logons from known application servers; it never applies to failures. Default empty. Logon type 3 stays excluded by default via `SuccessfulLogonTypes` [2, 7, 10, 11]. | "Ignore logon type 3 from known servers" without hiding failed logons. |
| 7 | 2026-11-21 | Security-log back-off | After consecutive failed Security-log reads the DC is retried after 1, 2, 4, 8, 16, then every 30 min. The bookmark only advances on success, so nothing is lost. Directory Service/DFSR logs and replication checks are not delayed. | A DC with a permission problem should not be hammered every poll, and one warning (1st and 6th failure) is enough in the log. |
| 8 | 2026-11-21 | DC samples | Parser tests use one full event per ID in `tests/NetWatch.Tests/Samples/Dc/<id>.xml`, written in the exact `EventRecord.ToXml()` schema with every EventData field of that event. They must be replaced by exports from the real DCs during the pilot (`wevtutil qe Security /q:"*[System[EventID=4625]]" /c:1 /f:xml`). | No real DC is reachable from the build machine. |
| 9 | 2026-11-21 | DC rules added | "User or computer account deleted" (4726/4743, Warning) and "Kerberos pre-authentication failures spike" (≥ 50 × 4771 on one DC in 5 min across all accounts, Major). "Account Operators" joins the default privileged groups. Upgrades get the new rules (the seeder adds missing built-in rules by name); an installation that saved its own privileged-group list keeps that list. | Brief WP2. The per-account (5) and per-source (20) rules already cover targeted guessing; the spike rule catches spraying that stays under both. |
| 10 | 2026-11-21 | Replication API | Replication data keeps coming from LDAP (`msDS-NCReplInboundNeighbors` over signed + sealed LDAP 389), not `System.DirectoryServices.ActiveDirectory.GetAllReplicationNeighbors`. Both return the same DS_REPL_NEIGHBOR data (partner, naming context, last success, last attempt, result, consecutive failures). | Keeps the ADSI/COM dependency out of the single-file exe and works with a least-privilege account; already pilot-ready since 1.3. |
| 11 | 2026-11-21 | Replication thresholds | "AD replication failing" now needs 1 h of continuous failure (was 15 min). New "AD replication stale": last success older than `ReplicationStaleHours` (default 3, Major); a link that was attempted but never succeeded counts as stale. | Brief WP3. Short transient failures (a DC reboot) no longer page anyone. |
| 12 | 2026-11-21 | Clock skew | Warning stays at > 30 s for 5 min; critical lowered from 240 s to 120 s. | Brief: alert at 2 min, well inside the 5-minute Kerberos limit. |
| 13 | 2026-11-21 | DC reachability | Every DC poll makes a TCP connect (3 s timeout, in parallel) to LDAP 389, Kerberos 88 and DNS 53; "DC service port unreachable" after 2 min (Major), per port. Results also stored in `DcInfo.ReachabilityJson` (migration Wp3DcHealth). The authenticated LDAP bind itself is exercised by the replication check, and its error is shown as the replication error. DNS uses TCP 53 (DC DNS servers listen on TCP too) so no DNS query library is needed. | Brief WP3, without new packages. |
| 14 | 2026-11-21 | Existing installs | Built-in rules that already exist in the database keep their stored thresholds on upgrade (the seeder only adds missing rules). Release notes tell administrators to set "AD replication failing" to 3600 s and "DC clock skew critical" to 120 s if they want the 2.0 defaults. | Never overwrite a rule an administrator may have tuned. |
